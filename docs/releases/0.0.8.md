## Durable Storage and Recovery

SinterDB 0.0.8 can keep its data on disk. Acknowledged writes survive a restart
or a crash, and the server recovers them on the next start.

```sh
sinterd --data-dir ./data
```

Without `--data-dir` the server behaves as before: everything stays in memory
and is lost on shutdown.

### Highlights

- **Write-ahead log.** Every change is recorded in a checksummed log before it
  is applied. An operation that changes several documents, such as
  `insertMany`, `updateMany`, or `deleteMany`, is one log record, so it is
  applied completely or not at all, even across a crash.
- **Two acknowledgement modes.** `fsync` (the default) acknowledges after the
  log is flushed to stable storage. `buffered` acknowledges after the write
  reaches the operating system, which is faster but can lose recent writes on
  power loss.
- **Startup recovery.** The server loads the newest valid snapshot and replays
  the log after it. An incomplete final record left by a crash is dropped
  without loss of acknowledged data.
- **Checkpoints and compaction.** Snapshots are taken automatically after a
  configurable amount of log and on clean shutdown, and old log segments are
  removed. The two newest snapshots are kept, so a damaged snapshot falls back to
  the previous one without data loss.
- **Safe failure.** Damage in the middle of the log, a snapshot, or the manifest
  stops startup with an error naming the file, byte offset, and log sequence
  number. Recovery is designed never to start with data that did not exist at
  some point, and never to modify a log it cannot trust. The fault-injection
  tests check this.
- **Directory lock.** Only one server can use a data directory. A lock left by a
  process that died is taken over automatically.
- **Storage format versioning.** The data directory records its format version,
  and a server refuses data written by a newer one.

### Options

| Option                   | Environment variable        | Default          |
| ------------------------ | --------------------------- | ---------------- |
| `--data-dir <path>`      | `SINTERDB_DATA_DIR`         | none (in memory) |
| `--durability <mode>`    | `SINTERDB_DURABILITY`       | `fsync`          |
| `--checkpoint-bytes <n>` | `SINTERDB_CHECKPOINT_BYTES` | 64 MiB           |

`--durability` and `--checkpoint-bytes` require `--data-dir`.

The `server.started` log now includes the storage mode, the data directory, the
durability mode, how many databases and collections were recovered, the
snapshot used, how many log records were replayed, and any damaged snapshots
that were skipped.

### Testing

- Crash tests start a real process, write continuously, and terminate it with
  `SIGKILL` at random moments and at each stage of a checkpoint, in both
  durability modes. After every kill they require the recovered data to equal
  the acknowledged writes, with at most the single in-flight operation applied.
- A separate test kills the real `sinterd` binary while three clients write
  through the driver.
- Fault-injection tests flip bits, truncate, delete, and overwrite log, snapshot,
  and manifest files, and require recovery either to produce a state that really
  existed or to refuse with a clear error.

### Changes to be aware of

- Storage failures, such as a full disk, are returned to clients as
  `InternalError` (9000) with an unknown outcome. They were previously reported
  as document validation errors.
- Database and collection names can be at most 255 bytes.
- When a data directory is configured, `SinterServer.catalog` only exists after
  `start()`, because starting is when data is recovered. A new
  `SinterServer.recovery` property reports what recovery did.
- Stopping a server with a data directory writes a final checkpoint, so shutdown
  takes longer for large datasets.
- Checkpoints run on the server's only thread and pause it briefly while a
  snapshot is written.

### Limits

- The whole dataset must fit in memory. Recovery briefly needs about twice the
  size of the snapshot it loads.
- The crash tests terminate the process, so they cannot prove that `fsync` mode
  survives a power loss. That protection depends on the engine flushing at the
  documented points and on the storage hardware honoring flushes.
- The directory lock is a file. It does not protect a directory shared over a
  network file system.
- There is no encryption, compression, or replication.

See [Durable Storage](../storage.md) for the full details, including recovery
errors and backups.
