## Indexes and Query Planning

SinterDB 0.0.9 adds indexes. Queries can find documents without scanning the
whole collection, and unique indexes enforce constraints.

```ts
await users.createIndex({ field: "email", unique: true });
await users.createIndex({ field: "age" });

const plan = await users.find({ age: { $gte: 18 } }).explain();
```

### Highlights

- **Single-field indexes.** `createIndex()`, `dropIndex()`, and `indexes()`.
  Indexes can be ascending or descending, `unique`, `sparse`, and on nested
  fields. Every collection has a unique `_id` index.
- **A query planner.** It chooses between a collection scan, an `_id` lookup,
  and an index lookup for equality, rang, and `$in` filter, including filters
  joined by `$and`. An index only narrows the candidates, so results, including
  their order, are identical to a scan.
- **Unique indexes.** Enforced on inserts, updates, replacements, upserts, and
  multi-document writes. A rejected write changes nothing, and two clients
  racing to write the same value cannot both succeed.
- **`explain()`.** `find(...).explain()` reports the stage, the index and access
  kind, range bounds, and an estimate of how many documents will be examined.
  The plan format is experimental.
- **`validateIndexes()`.** Rebuilds every index from the documents and reports
  any difference.
- **Durable definitions.** Index definitions are stored in the log and in
  snapshots. The indexes are built when the server starts, and startup stops
  with a clear error if a recorded unique index cannot be rebuilt.
- **Typed definitions.** `IndexDefinition<TDocument>` checks the indexed field
  against your document type and rejects `_id`.

### Wire protocol

- New commands: `createIndex`, `dropIndex`, `listIndexes`, `explain`, and
  `validateIndexes`.
- New error codes: `InvalidIndex` (6000), `IndexNotFound` (6001), and
  `IndexConflict` (6002). A unique violation returns the existing `DuplicateKey`
  (4001)
- The `server.started` log reports `rebuiltIndexes`.

### Upgrading

The storage format is now version 2. A data directory written by 0.0.8 is
upgraded in place the first time 0.0.9 opens it. The
upgrade is one way:
0.0.8 will refuse the upgraded directory with an "Upgrade" error. Back up your
data directory first if you may want to go back.

### Changes to be aware of

- A missing field counts as its own value in a unique index, so one document
  may lack the field. Use `sparse` to allow many. An explicit `null` is a
  different value from a missing field, unlike in MongoDB.
- Startup takes longer in proportion to the number and size of indexes, because
  they are rebuilt on every start.
- Building an index scans the collection on the server's only thread, so
  creating one on a very large collection pauses other requests.

### Limits

- Indexes cover one field. There are no compound, text, partial, or expiring
  indexes.
- Arrays are indexed as whole values, and `$in` falls back to a scan when an
  indexed document holds an array in that field.
- `$or`, `$nor`, `$ne`, `$nin`, `$exists`, and `$not` do not use indexes, and
  sorting is not accelerated by them.
- The whole dataset, indexes included, must fit in memory.
